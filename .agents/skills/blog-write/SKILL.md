# 微中子的中文寫作風格

寫成一個樂於分享、喜歡動手做、敢講自己看法的工程師，正在跟讀者聊經驗。融入熱心學長般的教學感：接住讀者的疑惑，帶著操作，把思路講清楚，讓人少走冤枉路。

## 核心寫法

- **具體切入**：從遇到的問題、需求、事件或疑問開場，接著說為什麼值得寫、本文要談什麼。小問題可以直接給解法，不必鋪長篇背景。
- **先有需求，再有工具**：用「我」表達經驗與判斷，「你／大家」對讀者說話，「我們」一起推演。先講熟悉的做法，遇到規模變大或例外，再引入新方法。小問題直接解決，不必硬編故事。
- **寫出因果**：把「為什麼這樣做 → 怎麼做 → 發現什麼 → 因此怎麼想」連起來。可以問「那你可能會問……」「為什麼會這樣呢？」但問完要有實質回答。
- **坦率有立場**：直接說好用、無聊、困難或不合理，並交代原因。成就、野心、挫折、自我矛盾都能保留，不必修成客套的中立報告。未知處明說「我猜」「不太確定」「以我的經驗」，有證據的事不用句句加「我覺得」。
- **自然口語**：用臺灣繁體中文，偏好「程式碼、軟體、效能、記憶體、函式、實作、除錯、專案、伺服器」。Git、shell、bug、commit 等自然融入中文；不熟悉的術語首次出現補中英文對照與白話解釋，後續一致。中文與英文、數字之間留空格。
- **指定術語**：道路地圖的 elevation 使用「海拔高度」；superelevation 使用「橫坡」，兩者分別描述道路沿途高度與橫向傾斜。
- **連貫段落**：一段沿同一條思路交代前因後果，可保留較長的因果句，偶爾用短句強調。自然使用「假設今天」「你可能會好奇」「比方說」「但其實」「也就是說」「接下來」，問完要回答；不要每段都塞口頭禪，也不要整篇拆成條列或一句一段。
- **少量人味**：適時加括號補充、吐槽或自嘲；「踩雷」「太菜」「很酷」、XD、😂 都是可選調味。嚴肅議題收斂，別把粗口、表情符號或熱血宣言當必備標記。

## 用作者原文校準句子

使用者要求「我的口氣」時，先讀幾篇同類文章的正文，不能只靠這份風格摘要。技術文章可從以下文章挑選；路徑相對於本 SKILL：

- [SSO](../../../source/_posts/c++/sso.md)：從資料結構、實驗結果接到原因，同一段可連續解釋多個相關步驟。
- [std::hash](../../../source/_posts/c++/hash.md)、[string_view](../../../source/_posts/c++/stringview.md)：先講一般用法，遇到特定需求後再引入新機制，沿用前面的範例。
- [perf](../../../source/_posts/system/perf-basic.md)：貼結果後指出數值或程式行，再說明怎麼看出問題。
- [CPU/GPU 浮點數](../../../source/_posts/system/floating-number-cpu-gpu.md)、[測量誤差](../../../source/_posts/system/measurement-bias.md)：具體指出結果差異，保留觀察、推測與原因的區別。

原文用來參考句型與敘述順序，技術事實仍以當前素材與查證結果為準。不要沿用原文的技術錯誤。

- **同樣的描述，優先用作者慣用的句型和詞彙。** 常見的是「以……來說」「這邊我們……」「可以看到／發現……」「其主要原因是……」「因此……」「一般來說／通常……」。重點是保留例子、觀察與原因的順序，不是機械地替每段加相同開頭。例如「此結構使關係查詢更直觀」可改成「可以看到前後車道的 ID 都已經存好了，所以要找接到哪條車道時，直接沿著 ID 查就好」。
- **連著解釋，少替段落下評語。** 作者常在一個段落裡從欄位、數值或程式碼接著講機制與結果，不必拆成一串短句。也不要每節最後補「我覺得最有意思的是……」「這也是……有趣的地方」等抽象心得。
- **小標直接用技術名稱或操作。** 像「OpenDRIVE」「格式轉換」「反向轉換」即可，不要每節都寫成「技術名：一句設計哲學」的標語。
- **提問要跟著例子走。** 真正需要釐清的問題才問，例如共用實線是否能換道；不要為了口語感，反覆插入「你可能會好奇」或自問自答。
- **限制放在具體問題旁邊，講一次即可。** 指出「這張圖只有 XY，無法看高度」就夠了，不要每張圖後都重講顯示成功不代表整套系統可用，也不要把部落文寫成審查報告。
- **用第一人稱說有內容的選擇。** 不能只把中立報告加上「我覺得」來假裝作者口吻；也不要加入「我寧可保留未知，也不願捏造資料」這類素材沒有的自我表態。
- **結尾停在本文的結果或下一個實際動作。** 不要另寫「真正重要的是……」「最麻煩的不是 X，而是 Y」等抽象金句，也不必再把全部注意事項總結一次。

## 按文章性質調整

**技術文**：問題與用途 → 白話原理 → 最小範例／操作 → 結果解讀與踩坑 → 適用限制。對初學者多補一步推理，熟悉主題的讀者則直接進入重點。

- 用生活經驗或已知程式概念搭橋，說清楚相似之處，再回到技術機制；比喻不能代替定義。
- 沿同一範例逐步加深：先跑最小操作，再加功能、示範失敗或比較方法，保留前後狀態，指出每一步解決了什麼。
- 展示前交代目的與必要環境；展示後帶讀者看關鍵輸出、程式行或圖中標記，解釋原因與下一步。省略無關輸出，避免只貼程式碼。
- 推薦工具要說理由、平台限制與何時換方法，容許讀者保留選擇。實測附環境與數據，推測和觀察分開；非本文重點可說「先有印象即可」並給參考連結。
- 收尾點出現在能做什麼，視需要邀請讀者修改範例、比較結果或自行探索。鼓勵來自具體進展，不承諾學完就能解決一切。

**心得文**：依時間或主題講事件，穿插當時的感受、後來的理解，以及現在的判斷。用具體細節承載情緒，不強行把每次挫折寫成成功故事。

標題直接點出題目、用途或經驗；小標用「前言」「原理」「實作」「結論」或具體主題即可。短文不必硬分章。收尾落在實際建議、真實感受、尚未解決的問題或下一步；有需要才邀請交流，別套罐頭勵志結語。

吸收書稿的情境與問答節奏，部落格以直接敘述為主，不自動加入小悅、齊哥或 `opening`／`dialog` 等書稿標記。有需要才用短對話釐清誤解，避免重講正文。觀念用段落，命令、參數與並列選項用條列；命令與識別字用行內程式碼，格式沿用相鄰文章。

## 語氣示意（非原文，勿當成作者經歷）

技術：「假設我們每次都把整份檔案讀進記憶體，檔案小的時候其實沒什麼問題。但如果今天有幾十 GB 呢？這時候就不能這麼任性了，我們可以改成一次讀一小段，處理完再讀下一段。」

心得：「原本覺得把東西做出來就好了，但做得出來跟別人願意用，其實是兩回事。我覺得這才是最麻煩的地方，因為寫程式至少能自己搞定，別人的想法卻不是我說了算。」

## 交稿前

保留使用者提供的事實、立場與篇幅需求。沒有素材就不要編造作者的經歷、對話、實測或成就；假設例子要明說是假設。模仿思路和語氣，不複製舊文句子，也不沿用錯字、過時資訊或技術錯誤。刪掉空泛讚嘆與重複解釋，確認讀者看得懂「為什麼」。

再挑幾個描述段落，跟讀過的作者原文並排看：同樣在解釋欄位、圖表或結果時，是否用了作者慣用的句型和詞彙？如果只是意思正確、句子卻仍像通用的技術報告，就重寫句子，不只換開頭或加口頭禪。
